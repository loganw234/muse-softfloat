Audited tree: `main` at a2241fc (2026-10-30 17:43 -0700), 185 commits, identical to `origin/main` at the time of the audit.
Auditor: an automated Claude Code audit session as lead, with seven reading subagents, each confined to one slice of the repository. Every finding below that carries a severity was re-checked by the lead against the tree, by probe or by command, before it was written down; findings the lead could not re-check are marked "agent-verified".
Environment: a clean Linux container (Ubuntu 24.04, x86-64, 4 vCPU, gcc 13.3.0, clang 18, Python 3.13.18, mpmath 1.4.1 in a venv, Node 22, arm-none-eabi-gcc 13.2.1 installed during the audit). Not available here: the owner's Windows host and MSYS2 path, the RP2040 boards and picotool, the pico-sdk, Berkeley SoftFloat/TestFloat, MPFR headers, zig/emscripten, the IEEE 754-2019 PDF, the kit zip, raw transcripts, and the scratch keys for the last eight verifier runs. ## 1. Summary

**The library computes correctly, as far as every independent check available here can tell.** On this host the project's own gates pass (smoke, standard, both sanitizer flavours, the ARM symbol scan, the host example). Beyond those, this audit wrote its own oracles, none of which reuse the project's generators or deciders, and found no arithmetic defect:

- 160,000,000 binary32/binary64 cases against the host's SSE2/AVX2+FMA unit in four hardware modes with flags compared exactly: the only divergence is `fma(±0, ±∞, qNaN)`, where the library signals invalid and x86 does not, which is the implementation-defined choice SF-0 2.5 records.
- All 2^32 binary32 inputs converted to binary16 in each of four modes against the F16C hardware instructions (17.2 billion conversions), and all 65,536 binary16 inputs widened: zero mismatches on bits and flags.
- 240,000 decimal and hexadecimal character conversions against CPython's correctly rounded converters: zero mismatches on bits, flags and consumed length.
- The eight Clause 9 functions (sinPi, cosPi, rSqrt, hypot, exp2, exp2m1, log2, log2p1) against mpmath at 320 bits with exact-rational rounding in all five attributes: zero mismatches over 160,000 binary64 cases, 160,000 binary32 cases, and every finite in-domain binary16 input (1,658,840 cases).
- The core reader's own evidence adds 28.8M host comparisons, 16M glibc comparisons for nextUp/nextDown/logB/scaleB, 12M cases against a Fraction oracle written from the standard, sanitizer sweeps of 340M calls, and a mutation check that caught 5 of 7 injected kernel defects (the other two are equivalent mutants).

Two real library defects were found, both outside any workload's reach, plus one proof-integrity finding in the Clause 9 kernel: the wide-arithmetic normalization is off by one and the "generator-proven" error bounds assume a normalization the code does not have; the bounds still hold with 5 to 11 bits of measured margin, and no wrong result was observed, but the derivation as written does not apply to the shipped code (M18). The two defects: the decimal/hex parser mis-converts inputs longer than about 100,000 digits (25,000 hex digits) when an explicit exponent should cancel the digit run, with no flag raised (M8); and the public Pico example runs the decimal converter, which needs about 2.4 KiB of stack, against the SDK's 2 KiB default stack (M7). Four low-severity contract issues are listed (out-of-range rounding argument, narrowed negative signaling NaN losing its sign, no `extern "C"`, a wrong ABI note).

**The weight of the findings is in claims, gates and record-keeping, not in the arithmetic.** The project's thesis is "the gate is the product" and its public text makes universal statements about its process. Several of those statements are contradicted by the project's own record:

1. The README and site say an independent verifier checked every parcel against a planted copy before it merged, with "pre-ledgered" defects. The IAS15 Pico firmware parcel, the headline workload, was merged with no verifier and no planted copy; Wave 1 merges preceded their verdicts; and for 120 of 160 plants no key hash was committed before the grades landed. The project's own final adherence audit calls the README sentence "disprovable from git log" and lists the fix as still owed (H1).
2. The README says each row is gated against Berkeley TestFloat, MPFR or an exact reference "at the volume its authority names", but no committed vector carries a Berkeley provenance tag, no budget or CI job runs the Berkeley or MPFR oracles, the Berkeley level-2 slices were take-capped, and the ledger's `testfloat-l2` label on 690 rows describes one-time lead runs in scratch that cannot be reproduced from the repository (H2). The record itself shows why this matters: Berkeley, not the project's own reference, caught the largest Wave 1 defect.
3. Two of the twelve permanent negative controls do not test what their names say: the count-mismatch control refuses even without its mutation (M1), and the stale-manifest control cannot detect a stale binary because the manifest is regenerated from the files under test in the same run and never binds the binary (M2). The MPFR deciders for the binary64 trig and exp/log vectors are broken on LP64 hosts, so the binary64 oracle path cannot run on Linux or in CI (M3). The three workload proofs, their pinned digests, the committed wasm and the two generated table headers sit under no gate at all (M4), and the one precedent in the record is exactly that failure mode (the demo's interval expectation went stale at the Wave 6 landing).
4. The record has integrity gaps the project's own auditors did not see because they never opened `lead.md`: entries were extended in place under earlier timestamps (M11); three planted sentences were landed as accepted brief corrections (M10); the frozen bundle silently dropped the entire KissFFT verification trail through a substring filter (M12); board results are recorded without the flags, commit and artifact hashes the project's own evidence rule requires, and the tooling never prints them (M13).
5. The public site still shows the superseded interval hash and timing as the current silicon result (M5); the demo extractor embeds verbatim REBOUND lines under an MIT label while the README says nothing redistributes REBOUND (M6); the clean-room claim is published without the owner-mandated waiver qualifier (M9).

What is unusually good: the headline numbers are reproducible to the digit (more than twenty were re-derived); the gate prints its inventory before any verdict and skips by name; `plants.jsonl` and `RECORD.md` are append-only in git with every miss and slip named; the disclosure habit is real. The remaining problem is that the public summary sentences are stronger than the record they summarise, and that the most important evidence (Berkeley, board, workloads, keys) is not re-runnable from the repository.

## 3. Findings

Severity: **high** = a public claim about correctness or process that the project's own record contradicts, or a defect in the thing the project says it is; **medium** = a real defect, a gate that does not test what it says, or a claim that would mislead a careful reader; **low** = contract, hygiene and documentation issues; **observation** = not a defect. Each finding names the file and line, the evidence, and the cheapest honest fix.

### 3.1 High

**H1. The public claims about the verification protocol are stronger than the record.**
README.md:109-112 says "before each piece of work merged, an independent verifier checked it against a copy carrying deliberate hidden defects"; README.md:286-288 says "a verifier that only disconfirms stands between each parcel and the push"; AGENTS.md:130-131 says "a verifier pass precedes every move of `main`"; site/index.html:99-101 says the defects were "pre-ledgered". The record says otherwise:
- The IAS15 Pico firmware parcel, the headline workload, was merged at d9718cf (2026-10-27) on the parcel's own READY with no verifier pass and no planted copy (`passes.jsonl` has author and surveyors only; `plants.jsonl` has no ias15-pico row; audit-bundle/ledger/lead.md:303 "No planted-copy verification was run for this branch"). There are 33 first-parent merges and 32 planted verifications.
- Wave 1 merges (2843792, 06fdec8 at 05:17-05:18) preceded key creation (05:23) and the verdicts (05:44, 05:49); RECORD:1000-1003 lists this as "still open and immutable".
- For 120 of 160 plants no key hash was committed before the grades landed (`git log -S<hash>` first hits the grade-landing commit; RECORD:1004-1005: "plant key hashes were never pre-committed"). The hash-only rule started with polish1 on 2026-10-29 and has held since (8 of 8 in order, 9m40s to 22m56s before the grades). The ledger-stamp fallback supports "before dispatch" for 12 of the 24 earlier runs and is undemonstrable for the other 12.
- The project's final adherence audit (audit-bundle/reports/audit-adherence-final/report.md:23-47) grades this "STILL OPEN ... README:141-144 still states the universal ... disprovable from `git log` ... Still owed (debt D4)". RECORD:1031-1033 says the false universals were restated, but only one README sentence and one HARNESS row were; the parcel-level wording and the AGENTS.md sentence survive.
Fix: restate the three sentences to what happened ("every Wave 2-6 parcel; Wave 1 and the IAS15 firmware parcel were lead-gated only; key hashes pre-committed from 2026-10-29 on"), and add the ias15-pico exception to the README's workload paragraph.

**H2. The merge gate does not exercise the executable semantic authority, and the README reads as if it does.**
README.md:140-145: "Each row is gated against Berkeley TestFloat 3e, MPFR, or an exact reference at the volume its authority names (411,213 committed vectors; `standard` adds 1,117,504 generated checks plus a 5,505,024-check ... differential)". Facts:
- No committed vector carries a `berkeley:*` provenance tag; every tag in the gate inventory is `exact-py*`, `exact-f64`, `exact-str`, `mpfr640-trig`, `mpfr-alg` or `mpfr-explog`. The 411,213 / 1,117,504 / 5,505,024 figures contain no Berkeley or TestFloat vector.
- `tests/berkeley_ingest.py` exists but nothing in `tools/`, `.github/` or `board/` invokes it; `tools/run.sh:10-11` ("oracle-priced sets join as the waves claim operations") never happened; the oracle builds live in `audit-bundle/lead-scripts/oracle*.sh`, which `cd` into the owner's scratch tree.
- `docs/COVERAGE.tsv` names `testfloat-l2` on 690 of 849 rows and `mpfr-hardest-*` on 117, but RECORD:412 and :500-501 say the level-2 slices were "largely take-capped" and "remain take-capped"; only level 1 is stated complete (RECORD:454-455). Three same-format `convertFormat` rows are labelled `berkeley` although Berkeley 3e has no same-format conversion and their vectors are `exact-py`. The twelve decimal/hex rows are labelled `mpfr-exact` but are decided by the Python `exact-str` reference ("MPFR cross-checks run separately in scratch", tests/gen_vectors_str.py:23-24). Of the 99 rows labelled `exhaustive-f16*`, only 13 operations are in the budgeted f16-exhaustive leg (65,536 × 14 = 917,504).
- RECORD Wave 1 shows why this matters: Berkeley, not the project's reference, caught the largest defect (tininess judged on the delivered value instead of Clause 7.5's unbounded rounding; the Python reference mirrored the same misreading, "so every self-consistent gate passed").
The Berkeley evidence exists in the record (37M+ cases in Wave 1, level 1 complete in Wave 2) and the audit's own hardware differentials corroborate it, but an external party cannot re-run any of it from the repository, and CI never runs it. Fix: wire `berkeley_ingest.py` into an optional `oracle` budget that SKIPs-BY-NAME when the pinned oracle tree is absent, record a per-row evidence class honestly in COVERAGE (`berkeley-l1-recorded`, `exact-py`, …), and reword README:140-145.

### 3.2 Medium

**M1. The count-mismatch negative control is vacuous as wired.** tools/run.sh:250-253 mutates line 1 of `expect.txt` (+1) and replays `encodings-f16.vec` alone, but `expect.txt` holds all 77 provenance tags of the whole corpus, so the runner prints 77 `COUNT MISMATCH` lines and exits 1 with or without the mutation (reproduced: rc=1 with the unmutated file). The runner mechanism itself is sound (a one-tag expect file passes at 2352 and refuses at 2353). By the project's own definition ("each watched to fail before it is trusted") this control was never watched failing for its reason. Fix: derive the control's expect file from the one file it replays.

**M2. The manifest and expect-count files cannot detect a stale binary or a changed corpus, and the manifest omits six compile inputs.** tools/run.sh:290-292 writes both files from the files under test and verifies them seconds later; the runner hashes files on disk and never itself, so an edited `src/` with a pre-edit binary still prints "manifest: all entries match / VERDICT: PASS" (test-harness reader's experiment). SF-0 5.2's "stale-binary replay (manifest hash mismatch must refuse)" is therefore exercised only as a text-mismatch control (control 5). Missing from the manifest: `src/msf_internal.h`, `src/msf_decode.h`, `src/msf_performat.inc`, `src/msf_trig_tables.h`, `src/msf_explog_tables.h`, `tests/sha256.h`. `--expect-counts` iterates only over the expect file's entries, so a tag that ran but is absent passes, an empty expect file passes, and tags of 64+ characters are truncated by `strncpy` (runner.c:134). Fix: embed a source-tree hash in the binary at build time and have the runner print and check it; commit per-file vector counts and hashes; make `--expect-counts` strict in both directions.

**M3. The MPFR deciders for binary64 trig and exp/log are wrong on LP64 hosts.** tests/trig_exhaustive.c:303-307 and tests/explog_decider.c:575-578 call `mpfr_set_ui(x, (unsigned long)sig)` and then add the high 32 bits again, on the assumption that `unsigned long` is 32 bits (true on Windows, false on Linux/macOS); every binary64 input with a significand ≥ 2^32 is doubled, so `sinPi(0.1875)` is decided as `sinPi(0.375)`. The test-harness reader built both against the runtime libmpfr: 412 of 1,600 and 1,842 of 4,000 mismatches, and the vector generators abort with UNDECIDED; with the one-line mask fix (`sig & 0xffffffffULL`, as tests/alg_decider.c:260,342 already do) both pass and regenerate `trig-*.vec` and `explog-*.vec` byte-identically. The committed vectors are correct (generated on Windows). Nothing in CI exercises this path. Fix: mask as in alg_decider.c and add a one-input self-test.

**M4. The three workload proofs, the site replay and the generated tables are under no standing gate.** `tools/run.sh` never references `demo/`, `interval`, `ias15`, `kissfft` or `site/`; `ci.yml`'s four jobs touch neither; `pages.yml` uploads the committed `site/` without rebuild or replay; the drift check covers four generated files but not `src/msf_trig_tables.h`, `src/msf_explog_tables.h` or the 51 committed vector files. The IW1 digest folds in counted library calls, so any `src/` change that alters op counts silently invalidates `demo/expected-interval.txt`; that is what happened at the Wave 6 augint landing (RECORD "Judge's map" entry: the committed expectation still carried the pre-augint hash and `demo/run_demo.sh host` failed on `main` until restamped). The interval leg needs no network and runs in under a second; `replay.mjs` runs in seconds; the table generators need only mpmath. Fix: add the interval leg, the wasm replay and the two table regenerations to `standard` (SKIP-BY-NAME where mpmath or node is absent).

**M5. The public site misstates the current silicon result.** site/index.html:148 still says "stream hash beginning `ce81d66e` on both sides; 7.92 s of workload-call time" for the interval workload; README:94,174, RECORD:1079-1081 ("new hash replaces `ce81d66e...`"), docs/BOARD.md:117-120 and demo/expected-interval.txt carry `ae04caf0…c1422` and 6,659,219 µs since 2026-10-30. The paragraph is hand-written (data.json regenerates counts only) and `index.html` was last committed 2026-10-29. Also stale on the page: "Decimal entry for binary16 rounds ties-to-even" (app.js:43,48 use `Math.round`, ties away from zero in magnitude: 1+2^-11 gives 0x3c01). Fix: restate the sentence or generate it from `demo/expected-interval.txt`.

**M6. Verbatim REBOUND (GPL-3.0-or-later) source lines are committed in an MIT-labelled file, and the README says nothing in the repo redistributes REBOUND.** demo/make_ias15_extract.py (SPDX MIT, line 2) embeds about 60 upstream lines as exact-match anchors for `replace()`/`drop_range()` (e.g. lines 157-170, 194-198); they must be byte-exact because the script asserts their occurrence count against the fetched file. demo/README.md:100-103: "this repository contains only the generator that extracts the pinned subset and our own glue - nothing here redistributes REBOUND". De minimis in scale, but the sentence is false as written and the licence label is wrong for those lines. Related: board/CMakeLists.txt:121-139 links the GPL extract with the MIT library and the Pico SDK into `msf_ias15.{elf,uf2}`; no release exists today, so no combined binary has been distributed, but `.gitignore:8` says firmware is "shipped as release assets" and nothing records that such an asset would be a GPL work needing its notice and Corresponding Source. Fix: match anchors by line hash or label the file; add one sentence on the firmware's licence.

**M7. The public Pico example runs the decimal converter against the SDK's 2 KiB default stack.** At the gate flags (`-Os -mcpu=cortex-m0plus`), `from_decimal_generic` uses 2,856 B of stack, `to_decimal_generic` 1,888 B plus `big_to_digits` 440 B, `log_core` 1,480 B (measured with `-fstack-usage`). The board firmware targets raise `PICO_STACK_SIZE` to 0x1000 for this reason (board/CMakeLists.txt:103,126,166,191), but examples/pico/CMakeLists.txt sets no stack size while examples/pico/main.c:41,52 call `msf64_to_decimal`/`msf32_to_decimal`. The example printed correctly on the board at its merge gate, which is consistent with an overflow into unused RAM below the core-0 stack. No header or document states a stack requirement. Fix: set `PICO_STACK_SIZE=0x1000` in the example and document per-family stack bounds (the string and log paths).

**M8. The decimal/hex parser mis-converts inputs longer than about 100,000 digits with no flag.** src/msf_string.c:381-398 clamps the explicit exponent at ±100,001 before combining it with the digit count, so an opposite-sign exponent that should cancel a long digit run is lost: `msf64_from_decimal("1"+"0"×100002+"e-100002")` returns 10.0 (0x4024000000000000, flags 00); with 200,000 zeros it returns +∞ with overflow; `msf64_from_hex("0x1"+"0"×25001+"p-100004")` returns 8.0. The file header (:6) says hex is converted "exactly ... of any length". Unreachable by any committed vector (longest line 847 chars) or workload. Fix: fold the digit count into the exponent before saturating, or reject inputs beyond a documented length with a flag.

**M9. The clean-room claim is published without the owner-mandated waiver.** docs/KICKOFF.md:196-198: the clean-room fingerprint audit was "waived by the owner because the fingerprint tooling was not finished before the hackathon began. This is a waiver, not a completed audit; the record must keep saying so" (also KICKOFF:113 "No mechanical fence exists"; RECORD:595-598). README.md:296 ("Developed clean-room from the standard: no third-party softfloat source is copied") and audit-bundle/README.md:36 ("clean-room by construction") carry no mention of the waiver; AGENTS.md never mentions it; the bundled audit does. Fix: one clause in each sentence.

**M10. Three planted sentences were landed as accepted brief corrections.** docs/metrics/corrections.jsonl rows 17-19 (verifier-sf2, `accepted: true`, labelled wave4) quote "616,754 to 594,666", "R1 (underflow not raised)" and "pack has no ties-to-away mode yet"; audit-bundle/plant-keys/sf2-draft.json shows these are the plants "augmented op-count evidence inflated", "owner pin P1 flipped" and "existing internal mode denied" (plants.jsonl rows 57-59), and the real draft dc9c986 reads 394,666 and "already correct under ties-to-away". RECORD:1022-1028 says planted candidates were "rejected with reason, not landed as corrections". The corrections metric (22 rows, all accepted) therefore double-counts plants; a genuine finding (the twiddledoc `kiss_fftr.c` hash, fixed at a41f026) has no row. Fix: append a correction row for the three rows and one for C5; the kit's own metrics tool would then count correctly.

**M11. Working-ledger entries were extended in place under earlier timestamps.** audit-bundle/ledger/README.md:21-24: "never edit an entry you already wrote: append a correction underneath instead". lead.md's entry headed "2026-10-28 05:24:40" contains "Measured (parcel-w5attr READY, appended same step): commit 8bfc877..." where 8bfc877 is dated 06:01:29, and cites 6e0f2f2/5e5591d (06:13:58); the 06:39:30 entry cites a0acf2a (08:58:10), 187541a and 53d2265 (08:55:26) and the alg2 key (e858498, 07:48:07); the 05:12:22 entry cites a 05:16:01 push. The lead's phrase "appended same step" discloses the practice, but the stamps no longer bound when the text was written, which is the property the ledger exists to provide. Neither project auditor opened lead.md (audit-adherence-final/report.md:12). ## 4. What was reviewed and found sound

So that the absence of findings is informative, this section lists what each reader checked carefully without finding a defect. Volumes are the readers' own runs unless marked "lead".

### 4.1 Core arithmetic (src/msf16.c, msf32.c, msf64.c, msf_roundpack.c, msf_wide.c, msf_decode.h, msf_flags.c)
