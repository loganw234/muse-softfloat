## 1. Executive summary

**Bottom line.** The numerical core is in unusually good shape, and the project's evidence discipline is real — its gates reproduce, its headline demonstration is true, and no secret was found anywhere in its history. The weaknesses are almost all in the *machinery around the evidence* and in a handful of statements that read stronger than the repository can reproduce. Nothing rated Critical was found; the single High concerns the test gate, not the library.

**What held up**

1. **Arithmetic and math functions: no defect found.** Against an independent exact-arithmetic reference the library produced **0 numeric or flag mismatches in ≈ 8.25 billion checks** (all 783 Tier-1 instantiations, five rounding attributes, cross-format forms, ties-to-away, 900,178 constructed exact ties); against MPFR the nine Clause 9.2/9.5 function families produced **0 mismatches in ≈ 8.2 × 10⁸ mode-checks** (binary16 exhaustive; five exhaustive binary32 binades; table headers regenerate byte-for-byte); against Berkeley SoftFloat 3e's own oracle **94 M further cases agree**. (A further Berkeley level-2 differential with fresh seeds, run by a separate agent, was still finishing when this version was written; its numbers are added in the next revision of this file.) Eight deliberately corrupted copies of the library were each detected, so a clean result means something. ASan/UBSan, valgrind, clang UBSan (44 M events), 13 compiler configurations and a wasm32 (ILP32) replay found no undefined behaviour.
2. **The headline claim is true — more strongly than stated.** Recomputing the project's own state hash from **stock, unmodified REBOUND 5.2.2** reproduces all 2,001 recorded IAS15 records (time, step sizes and every particle field) with zero mismatches, and the committed host, native and board captures are identical to each other. The Pico's output therefore equals the stock release's, not merely the project's extracted subset.
3. **The gates and CI are real.** `smoke`, `standard`, the full ASan+UBSan `sanitize` and the host example all pass here; GitHub Actions is green on `main`; every count in the README that could be checked (849, 783/66, 411,213, 1,117,504, 5,505,024, 153 of 160, 822 of 849, 576-entry manifest) is right.
4. **Hygiene that matters:** no credentials anywhere in 185 commits or the shipped bundle; no PDF and no audio track ever committed; the clean-room claim survives lexical and similarity scans against all of Berkeley SoftFloat 3e.

**What needs attention** (details in §4; `F-xx` are finding IDs)

1. **The gate has no external anchor (F-01, High).** Delete 90 % of a vector file, empty another, comment out 4,000 lines — the smoke vector step still prints `PASS` (411,213 → 343,077 vectors), because the manifest and expected counts are regenerated from the same files in the same run. A hand-made mutant that flips the sign of an exact-zero sum under round-toward-negative also passes the whole 411,213-vector corpus (F-05). Related: the README sentence that every row is "gated against Berkeley TestFloat 3e" is not true of the standing gates (zero Berkeley-tagged vectors; F-04) even though independent Berkeley re-runs agree; one negative control cannot fail for the reason it names, and the MPFR vector generators silently misbehave off Windows (F-06).
2. **Two wrong-value corners in decimal parsing, both outside the documented envelope (F-02, F-13).** A ≳ 100,000-digit token with an exponent returns a wrong value and bogus flags (an exponent clamp that ignores mantissa length; a verified six-line fix exists). Beyond 20 significant digits the parser rounds twice, so an exactly representable 55-digit decimal parses to a *neighbouring* double under the directed rounding modes and raises a spurious inexact. A small NaN-sign ruling contradicts SF-0's own wording (F-24).
3. **One memory-safety defect, in tooling and the firmware harness (F-03):** an over-long `internal.pack…` operation name overflows a 256-byte stack buffer in `hash_result()` (reproduced under ASan; the normal gate path is unaffected).
4. **Visible inconsistencies a reviewer will hit first:** the live demo page still shows the pre-Wave-6 interval hash and timing (F-07); the published `msf.wasm` carries 519 KB of debug data with the owner's `C:\Users\logan\…` paths and is not reproducible or gated (F-15); ≈ 60 lines of GPL-3.0 REBOUND text and constants sit under an MIT label (F-08); superseded video cuts are 74 % of a 273 MiB clone (F-09); the site's binary16 entry rounds ties up while the page says ties-to-even (F-22).
5. **Cost is not disclosed (F-11, F-12).** SF-0 §8 promised a "cost of conformance" report and a ≤ 2× budget against ROM routines; neither exists. Host measurements show binary64 add/mul 7–8× and **division ≈ 200×** slower than Berkeley's on the same machine (bit-serial restoring division), and the project's own figures imply ≈ 6,000 cycles per operation on the board. Worst-case stack is ≈ 3 KB while several RP2040 targets keep the 2 KiB default.
6. **Board evidence is thinner than the rule it cites (F-10):** RECORD quotes truncated artifact-hash prefixes with no build commit or flags, and the "968/968 on all six chips" set contains no arithmetic at all.

**Counts.** Critical **0** · High **1** · Medium **14** · Low **10** · Info **1** (grouped, seven sub-items). 26 numbered findings; 11 agents; ≈ 9 × 10⁹ independent numeric checks.

**Fix first** (each ≈ ≤ 1 hour; full list in §6): (1) correct the live page's interval card; (2) re-word or wire the Berkeley claim; (3) strip and republish `msf.wasm`; (4) commit a vector-corpus baseline and assert it in `tools/run.sh`; (5) label the REBOUND-derived generator and tables and add a licence map; (6) clamp the `hash_result` buffer; (7) add `extern "C"` to the public header; (8) apply the verified string-parser patch; (9) add the five supplied kill-vector files; (10) add a measured "cost of conformance, stack and size" paragraph.

## 2. Scope, method and limits

**Target.** `loganw234/muse-softfloat`, `main` at commit `a2241fc` (2026-10-30), tree identical to the session branch. The repository is a clean-room IEEE 754-2019 softfloat library in C for binary16/32/64 (849 declared "instantiations"), aimed at the RP2040 / Cortex-M0+, together with its test corpus and generators, a front-door gate script (`tools/run.sh`), plans of record (`docs/studies/SF-0/1/2.md`), an AEABI compatibility layer and RP2040 firmware, a WebAssembly demo site, host demos (REBOUND IAS15, KissFFT, an interval workload), a rendered demo film, and a frozen `audit-bundle/` of process evidence (577 files).

**How the audit was done.**

1. *Gates reproduced.* The project's own front door was run in a fresh clone on Linux (gcc 13.3, Python 3.13): `smoke`, `standard`, `sanitize` at the **full** ASan+UBSan flavour (which the owner's Windows host cannot link), and the host example. GitHub Actions history was read through the GitHub API.
2. *Eleven independent audit agents,* each with a disjoint scope and a shared rules file (read-only on the repo, work in private copies, honour the `cft` path rule in `AGENTS.md`, report evidence not suspicion): differential testing against Berkeley TestFloat (`oracle-diff`), an independent exact-arithmetic reference (`exact-diff`), MPFR for the Clause 9.2/9.5 functions (`math-diff`), decimal/hex string fuzzing (`strings`), API/generators/portability (`api-portability`), test infrastructure and gate strength (`test-infra`), mutation testing (`mutation`), claims-versus-reality (`docs-claims`), security/supply chain/secrets (`security-code`), licences/media/history (`legal-media-history`), and AEABI/firmware/examples/site (`board-site`).
3. *Lead's own checks* (not delegated): static analysis (gcc `-fanalyzer`, clang `--analyze`, clang-tidy), valgrind, auto-init pattern/zero builds, `ruff`, `shellcheck`, a host performance micro-benchmark against Berkeley SoftFloat, an **independent replication of the headline IAS15 claim against stock REBOUND 5.2.2**, offline reproduction of the interval workload, byte-comparison of the live GitHub Pages site with the repository, GitHub Actions/release/PR state, sampled film frames, and a full history mirror.
4. *Re-verification.* Every finding rated Medium or above in this report was re-checked by the lead by reading the cited lines or re-running a reproduction unless it is explicitly labelled "agent-reported". The evidence label on each finding says which.

**Independent oracles used.** Berkeley SoftFloat 3e and TestFloat 3e (the project's pinned archives; their SHA-256 values match `docs/metrics/fetches.jsonl`; built with the 8086-SSE specialisation), MPFR 4.2.2 via gmpy2, exact rational/bigint arithmetic written independently of the project's generators, CPython, glibc, and stock REBOUND 5.2.2 from PyPI.

**Limits you should know about.**

* No RP2040, no ARM GCC, no pico-sdk and no ARM emulator were available. Everything target-specific (stack, size, ABI, link behaviour) was estimated with clang for `thumbv6m-none-eabi`; board-side digests, the six-chip sweep and silicon timings could not be checked. Host halves of the board claims were reproduced.
* The IEEE 754-2019 PDF is not available, so statements about the standard are from memory and are labelled with a confidence where it matters.
* The container's network policy returns 403 for GitHub archive downloads, so the REBOUND and KissFFT legs of `demo/run_demo.sh host` (README step 4) could not be run. The interval leg of that script *was* reproduced offline.
* The provided checkout was a **shallow clone** (90 of 185 commits). All history-dependent checks (cited commit hashes, blob sizes, secrets/PDF/audio in history, authorship) used a full bare mirror of the remote: 185 commits on `main`, 119 first-parent, four refs (`main`, `wave6-ci`, `wave6-examples`, `wave6-sanitize`; the last three are fully merged), no tags. `git fsck --full` is clean.
* A memory-sanitizer runtime is not installed here; valgrind and auto-variable-initialisation builds were used instead.
* Nothing with `cft` in its name exists in the tree or in history (count 0); the rule was honoured throughout. The owner's clean-room fingerprint audit against that reference was **waived** (`docs/KICKOFF.md:196-198`), so clean-room status against it is a recorded waiver, not a completed check; the lexical/structural comparison here was against Berkeley SoftFloat 3e only.
* This is an engineering audit, not legal advice. Agent reports were returned as text; their raw harnesses and logs are kept under the scratchpad paths listed in Appendix B.

### 4.2 High and Medium findings

#### F-01 — The vector gate has no external anchor *(High · R-lead · TI-1)*

* **Where:** `tools/run.sh:156-172` (`write_manifest`, `write_expect_counts`), `:290-294` (written and verified in the same run), `:282` (static `VECS`), `:105-113` (drift check covers only 4 generated non-vector files); `tests/runner.c:645-672`, `:686-690`, `:898-910`.
* **What:** the manifest (SHA-256 of sources and vectors) and the expected per-provenance counts are produced from the very files the runner then verifies, in the same invocation, so neither can fail on tampering. The only committed numeric expectation is the instantiation inventory (783 / 66). `411,213` appears in no gate (only in `README.md` and `site/data.json`).
* **Lead reproduction** (runner built as `smoke` builds it; manifest and expect-counts regenerated each time exactly as `run.sh` does): untouched → 411,213 PASS. Keeping 10 % of `aug-f64.vec` → **369,678 PASS**. Additionally emptying `trig-f64.vec` → **347,068 PASS**. Additionally commenting out 3,991 lines of `arith-f32.vec` → **343,077 PASS** (all `rc=0`). The test-infra agent also showed duplicate files/lines, LF/CRLF swaps, a truncated provenance tag and an injected `# compare=nan-class` all passing, and that **consistently mutating a library branch *and* rewriting the 1,196 now-failing expectations from the runner's own output yields a green gate (411,213/411,213)** — while pinned Berkeley flags 165 mismatches in the rewritten lines.
* **Why it matters:** `AGENTS.md` calls the gate "the product". The replay itself is a genuine regression test (the corpus does see real defects), but an AI-driven workflow could weaken tests invisibly, and the SF-0 §5.2 "stale-binary / tampered-vector" controls cannot fail in `smoke`. The "stale manifest" control checks that a *corrupted manifest* is refused, not that a *tampered vector file* is.
* **Fix:** commit a baseline (`tests/vectors/BASELINE.tsv`: per-file SHA-256 and per-file/per-provenance counts), have `run.sh` assert total, per-file counts, `skipped-planned == 0` and the expected `compare=` mode, and add a regenerate-and-compare leg for the 42 pure-Python vector files (≈ 20 s). Updating the baseline then becomes a visible, reviewable act.

#### F-02 — String parser: exponent clamp ignores mantissa length *(Medium · R-lead · ST-1)*

* **Where:** `src/msf_string.c:381` (`#define EXP_CLAMP 100000`), `:383-405` (`parse_exponent`), used at `:545`, `:737`, combined at `:562`, `:566`, `:748`. Comments at `:378-380` and `:5-6` ("exactly for hex input of any length") are false at this size.
* **Lead reproduction** (binary64, round-to-nearest-even): `"1"` + 100,001 zeros + `"e-100002"` (true value 0.1) → `0x3ff0000000000000` (1.0), flags 00 — should be `0x3fb999999999999a`, inexact. `"1"` + 200,000 zeros + `"e-200000"` (= 1.0) → **+∞, flags overflow|inexact**. `"0."` + 200,000 zeros + `"1e200001"` (= 1.0) → **0, flags underflow|inexact**. A 1,000-zero control is correct. The strings agent found the smallest failing mantissas at 99,680 digits (binary64) and 99,996 (binary16), and similar failures for hex at ≈ 25–30 k digits.
* **Why the gate cannot see it:** the project's exact reference clamps identically (`tests/gen_vectors_str.py:285-286, 374-375`), and the longest committed string vector is 774 characters.
* **Impact:** silent wrong results (and bogus overflow/underflow flags) for ≥ ≈ 100 kB tokens; no memory-safety consequence. #### F-03 — `hash_result()` stack-buffer overflow *(Medium · R-lead (runner), R-agent (firmware) · SC-1, BS-1; related BS-8, BS-9)*

* **Where:** `tests/runner.c:145-158` (`char line[256]; n += snprintf(line + n, sizeof(line) - (size_t)n, "%s", opname)`), reached from `process_pack_line` (`:216`) for any token that merely *starts with* `internal.pack` (`:499`, `strncmp(tok[0], "internal.pack", 13)`), and an identical pattern in the RP2040 firmware `board/harness_main.c:76-93`, `:154-176` (USB-CDC command path) and `:97-112` (`hash_pair_result`).
* **What:** `snprintf` returns the *would-be* length. With a name longer than 255 bytes, `n ≥ 256` and the next call's size argument `sizeof(line) - n` wraps to ≈ 2^64 while `line + n` points past the array, so the following writes land beyond the buffer at an attacker-chosen offset.
* **Lead reproduction (host runner, ASan):** a vector line `internal.pack` + 300 `A` + ` te 0 0 1 0 -> 0000000000000000 00 prov` in `hash` mode → `AddressSanitizer: stack-buffer-overflow … WRITE of size 18 … hash_result tests/runner.c:152 … offset 345 overflows 'line' [32, 288)`. The same line in `verify` mode (the gate) is an ordinary FAIL, and a legitimate pack line passes with whole-run hash `577d57d9…`. The board-site and security agents reproduced the firmware path under ASan by compiling the unmodified `harness_main.c` against stub pico headers (the fuzzer hit it independently); it was **not run on silicon**.
* **Impact:** a crafted line crashes the host `hash` tool or corrupts the firmware stack of a dev board attached over USB. No committed vector triggers it and no recorded evidence is affected; blast radius is small (trusted host, no secrets).
* **Fix:** accept exactly `internal.pack16|32|64` with `strcmp`, clamp `n` after each `snprintf`, answer `E malformed` for over-long tokens, and add a negative control (an over-long op token must be refused).

#### F-13 — Beyond 20 digits the decimal parser rounds twice *(Medium · R-lead · ST-2, ST-4)*

* **Contract:** `include/muse_softfloat.h:33-34` promises correct rounding only for 1..H digits (H = 20); the beyond-H route (`src/msf_string.c:563-576`, `RECORD.md:540`) rounds the digit string to 20 digits under the active attribute and then converts. That is a documented limit; its consequences are not documented.
* **Lead reproduction:** the 55-digit exact expansion of the double 0.1 (`0.1000000000000000055511151231257827021181583404541015625`, exactly representable): ties-to-even → `0x3fb999999999999a` but **flags `inexact`** (correct: none); **toward-zero → `0x3fb9999999999999` (wrong), toward-positive → `…9b` (wrong), toward-negative → `…99` (wrong)**; ties-away right bits with spurious inexact.
* **Agent measurements (2,992,680 comparisons vs its own exact reference):** the library equals the literal two-step reference 100 %; ≤ 20 digits equals exact single rounding 1,143,960/1,143,960; for > 20 digits the library differs from exact for 26.5 % of exact-midpoint strings, ≈ 10–11 % of midpoint ± 1e-30, 13.9 % of near-binary strings, 3 of 169,815 plain random 21–40-digit strings. Boundary ties: exactly 2^-1075 (752 digits) → `0x1` (correct `0x0`); exactly max-finite + ½ ulp (362 digits) → max-finite without the **overflow flag**. Of 3,000 random binary64 values written with > 20-digit exact expansions, directed modes recover the value 1/3000 times and `inexact` is spuriously raised 2,999/3000 times. `to_decimal` with precision > 20 zero-pads after 20 correct digits (differs from a true correctly rounded P-digit string in 75–99 % of samples) and accepts precision up to `INT_MAX`.
* **Impact:** exactly representable long decimals (e.g. output of an exact printer, or constants copied from high-precision sources) parse to a neighbouring value under directed rounding. IEEE 754 permits a limit H on mandatory correct rounding, so this is within the letter of the contract; the cost of removing it (≈ 768 significant digits plus a sticky for binary64) is ≈ 120+ limbs and ≈ 1 KB more stack — a genuine trade-off.
* **Fix:** document the consequences beside the header sentence (and in `COVERAGE.tsv`, which lists the string rows as `mpfr-exact` with no mention of H); consider clamping or rejecting precision > H in `to_decimal`.
