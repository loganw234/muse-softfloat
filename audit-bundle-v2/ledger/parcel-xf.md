### Special-value tables per family (Clause 6 and 7 by number; SF-0 2.5 NaN matrix)

Common to all arithmetic and convertFormat: NaN delivery is msf_nan_delivery in operand position order (fma order multiplicand, multiplier, addend): first signaling NaN wins, quieted, invalid signaled; else first quiet NaN wins, no invalid for the NaN itself; else an invalid operation with no NaN input delivers the dest default quiet NaN with invalid. Payload mapping is by trailing-field shift into the dest format: f16 payloads widen by left shift into f32/f64 exactly; an f64 payload narrowing to f32 right-shifts with truncation, and truncation to zero payload delivers the default quiet NaN with no extra invalid. The delivered NaN sign is the source operand's sign; subtraction does not negate a delivered NaN (landed Wave 1 reading). Quiet bit is set on every delivered NaN. Flags below are in addition to that matrix.

add/sub (5.4.1, 6.1, 6.3, 7.2, 7.4, 7.5): inf + inf of opposite effective signs is invalid, default qNaN. One inf operand delivers that inf with effective sign (sub negates the second operand's effective sign, including its zero/inf sign). Finite cases compute the exact sum/difference and pack once. Exact zero: (+0)+(+0)=+0, (-0)+(-0)=-0, mixed-sign zeros and exact cancellation x-x give +0 except -0 under roundTowardNegative. Overflow/underflow/inexact only from the single pack, tininess after rounding in the Clause 7.5 unbounded-rounded sense (lead ruling 2026-10-26 22:14, already in msf_roundpack.c).

### No-double-rounding argument per family

Every source is decoded by msf_decode to exact sign, integer significand, exponent in its own format; no source is converted to any floating format before the operation, which is the whole point for f64-source to f32-dest rows. add/sub/fma: msf32.c add_mag normalizes each exact term with top bit at position 126 and aligns the other by jam shift; msf64.c add_terms aligns both terms in a 118-bit window under the dominant top, exact shift when the term reaches the window and jam shift only when its top is far below, where the jam bit sits below every bit the pack rounding decision reads (lead-stated bound: gap at most 65 keeps a 53-bit significand whole; larger gap keeps the jam bit at least 60 bits below the result top, pack needs p+2). A jam shift records discarded nonzero-ness in bit 0; it is sticky capture, not a rounding to a format. mul: exact integer product, exponents add. div/sqrt: wide integer quotient/root with remainder zero-ness as sticky into the pack; the pack reads guard/round/sticky from a width far beyond dest precision (f32 div quotient 128 bits, f64 about 122 bits; sqrt root 61+ bits for f64, 64-bit trial root for f32), so the single pack decision equals rounding the exact real result. convertFormat from_f16: decoded exact value packed once. Comparisons: no rounding anywhere; msf_cmp_finite compares (sig, exp) pairs exactly, and its equal-top alignment shift is bounded by the other significand's bit length (at most 53), so no bit is ever lost for any format mix. In all families the only rounding event is msf_pack_f32/msf_pack_f64 (msf_pack_generic), one call on the finite path.

### Width re-derivation for f16 sources (docs/WIDTHS.md classes unchanged)

Decoded f16 significands are at most 11 bits (hidden bit included), against 24 (f32) and 53 (f64), so every landed width bound only slackens: exact products stay at most 106 bits, reached only by fma triples f64 x f64 + f16; add_mag's normalize-to-bit-126 invariant (input bit length at most 106, hence at least 21 trailing zeros) is preserved with more margin; add_terms' 118-bit window bound is unchanged. Division and sqrt kernels normalize from bit lengths in [1,53]; f16 lengths in [1,11] stay inside those ranges (f64 div scale = 122-(la-lb) reaches 174 when a 1-bit f16 subnormal significand divides a 53-bit one; the loop bounds and the quo bit guard i<128 already handle that range because the true quotient top stays near 2^122 by construction). No WIDTHS.md class needs widening, and that file is off-limits to me in any case; if gating contradicts this paragraph it is an escalation, not an edit.

### What this brief got wrong

One wording point, objected here before coding around it and also sent urgent: the brief asks for convert-then-operate traps "at least one per arithmetic family per dest". For dest f64, converting sources to the dest format first is exact for f16 and f32 sources and identity for f64 sources (the brief's own load-bearing paragraph says the same), so for add/sub/mul/div/sqrt to f64 the convert-first pipeline provably never differs from exact-then-round, and no such trap exists to construct. My substitution, named so the lead can strike it: dest-f64 traps discriminate against the two intermediate-rounding hazards that do exist there, (a) fma evaluated as separately rounded mul then add, and (b) evaluating the operation at binary32 precision and widening the result; each dest-f64 arithmetic family gets at least one counted trap against (b), fma against both, and the generator also verifies on sampled sweeps that convert-to-f64-first agrees everywhere (count reported as zero differences, by construction). Source code is unaffected by this objection either way; I proceed with src and dest-f32 traps now and will reshape only test files if the lead rules otherwise.

Believed: residual risk concentrates in (i) the jam/window exactness arguments at the new exponent mixes (f16 tiny exponents against f64 extremes), which the seeded sweeps plus boundary-directed pools are built to falsify, and (ii) NaN payload narrowing f64 to f32 at the truncate-to-default boundary, covered by directed payloads (payloads just above and below the surviving-bit threshold).
